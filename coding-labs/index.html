Coding Labs

Twenty-two production-style backend components to implement yourself, in Java and in Go. Each one comes with a written contract, a diagram, a starter stub, a test suite that checks the contract, and a reference solution to compare against afterwards.

Open the labs Source on GitHub

01

What is in a lab

Small components of the kind a backend actually runs on: a blocking queue, a rate limiter, an outbox, a route planner. Each is scoped to be built in a sitting and still have edges worth getting wrong.

  • A contract

    The task, the API, the rules and a worked example, written down before any code. Every lab page also has implementation steps and a checklist.

  • A diagram

    Every lab has one, showing the structure or the timeline the contract talks about.

  • Starters in Java and Go

    IntelliJ IDEA projects with the public API in place and every method body left as a TODO: Gradle on JDK 21, and a Go module run with -race.

  • Tests that check the contract

    They fail out of the box. A supplied suite finds the boundary you skipped, the tie you broke differently, the interleaving you never imagined.

  • A reference solution

    For both languages, with the full test suite, to read only after your own version passes.

02

Four steps per lab

The order matters more than the code.

  1. Read the contract and the tests.

    List the inputs, outputs, boundaries, invariants, failure behaviour and limits before writing anything.

  2. Implement the starter.

    Replace every TODO. Run the lab's tests and fix what fails before reading anything else.

  3. Compare.

    Open the reference solution and explain one difference in representation or synchronization.

  4. Change something.

    Add a test for an edge case you chose, or implement the variation the lab page suggests.
